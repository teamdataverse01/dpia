# Decisions log

Choices made where the PRD was silent or ambiguous. The PRD's own **[ASSUMPTION]** items (section 17) are implemented as written and are not repeated here, except where we had to go further.

| # | Topic | Decision | Why |
|---|---|---|---|
| D-01 | Framework | Hand-rolled front controller + router (`src/Http`), no Slim. Only dev dependency is PHPUnit. | PRD 4 allows it; fewer dependencies for CU to maintain. |
| D-02 | Database | PostgreSQL. PostgreSQL-only syntax is limited to `GENERATED … AS IDENTITY`, `INSERT … RETURNING id` (`PdoConnection::insert`) and the audit-log trigger (`0002`). Each is commented with its MySQL equivalent. | PRD 4 / 17.6. |
| D-03 | Schema additions | Beyond the PRD DDL: `created_at`/`updated_at` on every table; `risk_entities.cleared_categories`, `residual_calculated_at`, `submitted_at`; `vendor_profiles.vendor_portal_user_id`; `control_assessments.evidence_original_name`, `evidence_mime`, `notes`, `source`; `approvals.approver_role`, `residual_rating_at_decision`; `remediation_actions.completed_at`; `factor_score_breakdown.framework_version`; `activity_templates.source_entity_id`, `created_by`; `scoring_config.change_note`; extra CHECKs (entity type, control category, risk acceptance needs a date, template vendor needs sharing). All are marked `-- added:` in `0001_core_schema.sql`. | Needed for the dashboard stories, approval rounds, the Vendor role's "own record", and the audit trail. |
| D-04 | Arithmetic | Weights are stored as percentages. The inherent score is `Σ(weight% × score) / Σ(active weight%)`, divided once, then rounded to 2 dp. The residual indicator is computed in hundredths and basis points. Bands are compared in hundredths. | Exact results (3.85, 3.83, 1.35) with no float drift. |
| D-05 | Residual indicator bounds | `residual_score` is clamped to ≥ 1.00 and `residual_score_100` to 0–100. | The PRD formula can otherwise go below the 1–5 scale. The rating is unaffected. |
| D-06 | Vendor score used by a DPIA | Uses the vendor's `residual_score_100` when present. Otherwise it is derived from the vendor's inherent score with the same 9.4 formula. A vendor with no score cannot be linked. | 7.1 says "current residual rating/score". Every scored vendor has a residual (see D-10). |
| D-07 | Vendor inputs | Sending `legal_basis`, `involves_data_sharing` or a vendor link for a **vendor** assessment is rejected (422), not silently dropped. | "Do not invent behaviour": the clearest signal to API callers. |
| D-08 | Clearance (9.2) | A category is cleared only when (a) every recommended **mandatory** control in it meets the criteria **and** (b) at least one recommended control in it meets them. An empty category is never cleared. | Without (b), a category with nothing recommended would be cleared vacuously and cut the risk for free. |
| D-09 | `not_applicable` | A mandatory control marked *Not applicable* does not satisfy clearance. | Prevents clearing by opting out. Admins can make a control non-mandatory or narrow its trigger instead. |
| D-10 | Controls that count | The controls that count for clearance are the currently recommended ones (risk trigger or template standard set), plus manually added ones treated as **non-mandatory** (they can help, never block). Rows for controls that are no longer recommended are kept for the record but ignored. | Supports "control selection" (MVP scope) without letting extra work block clearance. |
| D-11 | When residual is computed | The residual rating is recomputed on every scoring and control change (with no controls it equals the inherent rating, per the 9.3 `n = 0` rows). The **status** `residual_calculated` is set only by the explicit "Confirm residual risk" action. | The dashboard always has a residual basis, and the workflow step stays explicit. |
| D-12 | Factor-option score edits | Changing an option's score creates a new `scoring_config` version (same JSON, with a note). | Assessments then show they were scored under an older framework until recalculated (PRD 12). |
| D-13 | Derived permissions | Besides the six matrix columns: **View** (owners, operational roles, auditors); **ViewDashboard** (institution-wide: Privacy/DPO, Risk Approver, Admin, Auditor, per PRD 11); **ConfirmNegligible** (Reviewer, Risk Approver); **VerifyEvidence** (Reviewer); **SaveTemplate** (Privacy/DPO); **Decide** (roles in the approval routing for the residual tier); **ManageRemediation** (control editors and record owners); **Submit** (record owner). Admin can do everything. Records a user may not view return **404**, so they don't leak that the record exists. | Each comes from a sentence elsewhere in the PRD. |
| D-14 | Business Owner scope | A Business Owner mapped to a department (in `user_roles.department_id`) sees and edits only that department's records. With no department, they see all. | Uses the department column the PRD already has in `user_roles`. |
| D-15 | Vendor role "own record" | Matched on `vendor_profiles.vendor_portal_user_id`. | The PRD has no other link between a vendor user and a vendor record. |
| D-16 | Approval routing vs. matrix | The matrix grants "approve / accept risk" only to the Risk Approver. Section 16 routes Medium/Low approvals to the Privacy Team and Reviewer. Implemented as: **approve/reject** may be given by any role in the routing list for the residual tier, and every listed role must approve in the current round (since `submitted_at`). Any rejection rejects. **Accepting the risk** additionally needs the matrix "approve / accept risk" permission (Risk Approver or Admin) and an end date. An Admin's approval satisfies all roles. | Honours both sections. Confirm with CU (PRD 17.7). |
| D-17 | Review dates | On approval, `next_review_date` = today + the tier's review interval. On risk acceptance, it is `accepted_until`. | PRD 13 intervals. |
| D-18 | Monitoring transitions | `approved`/`risk_accepted` → `monitoring` and → `reassessment_due` (review date reached) happen in the daily job (`php bin/console jobs:daily`), audited as actor `system`. "Start reassessment" moves a decided record back to `scored`, keeps factors, controls and history, and withdraws any Very Low confirmation. | Lifecycle in PRD 6. Run the job daily from cron. |
| D-19 | Factor screens | "Risk Factors" and "Third-Party & Transfers" are separate screens. The first screen's answers are kept in the session until the second is saved, because `risk_factor_inputs` columns are NOT NULL. | Keeps the PRD's 10-screen plan and the schema. |
| D-20 | Vendor picker without JS | Without JavaScript the picker is always shown. Choosing a vendor while answering "No" to sharing is rejected with a plain explanation (7.1 rule 1). With JS, the picker is hidden and disabled unless the answer is "Yes" (7.1 rule 4). | Works with and without JS. |
| D-21 | Template signatures | data types = sorted, comma-joined keys; data subject = option key; characteristics = `nature=…;adm=…;cross_border=…;third_party=…`. Name matching ignores case, extra spaces and dash style. "Customised" is set only when saved answers differ from the template (not merely on opening Customise). | PRD 10 deterministic, explainable matching. |
| D-22 | Template re-score | The bulk re-score also sets `last_reviewed_at` to today. | An administrator re-scoring counts as a review. |
| D-23 | Data types | Stored as `factor_options` rows with `factor = 'data_type'`; their score is ignored. | Admin-editable like other options. The table requires a score. |
| D-24 | "Active" risks | Scored (has a rating on the chosen basis) and not `rejected`. There is no archived state in v1. Items without a department are counted under "Unassigned", so department totals always equal the overview total. | PRD 11.1–11.2. |
| D-25 | Dashboard stories | The control-effectiveness story uses the average `risk_reduced_pct` where each category is cleared, plus the count of items with only Policy cleared that are still Medium/High. True "time-to-Low" is **not** computed: there is no reliable per-item history of rating changes yet. The trend compares the latest snapshot with the latest one at least 90 days older (otherwise the earliest), and hides when a date filter is applied. Wording is in `config/stories.php`. | Only shows what the data supports (PRD 11.4). |
| D-26 | Demo snapshot history | The demo seeder inserts one **synthetic** historical `risk_snapshots` set (~95 days ago) so the trend story can be seen. Real installs start with none. | Demo only. |
| D-27 | Extra API endpoints | `GET /session` (user + CSRF token), `POST /score-preview` (live preview, no writes), `POST /risk-entities/{id}/start-controls`, `POST /risk-entities/{id}/controls/{cid}/verify`, `POST /risk-entities/{id}/residual` (explicit stage 6), `POST /risk-entities/{id}/reassess`. | Needed for the workflow; PRD 14 lists no equivalents. |
| D-28 | Charts and CSP | Strict CSP (`style-src 'self'`, no inline styles), so bars are SVG `<rect>`s with `<title>` tooltips, and every chart has a table next to it. | Security and accessibility. |
| D-29 | Evidence | Allowed: pdf, docx, xlsx, png, jpg/jpeg, csv, txt. The detected MIME type must match the extension. Max 10 MB (`EVIDENCE_MAX_BYTES`). Stored name is 32 random hex characters, outside the web root. Replacing evidence keeps the old file (for the audit trail) and clears verification. Evidence date defaults to the upload date. | PRD 15. |
| D-30 | Remediation | The person assigned an action can update its status and progress but cannot re-plan it (owner, date, priority). Completing sets 100% and `completed_at`. | Least privilege. |
| D-31 | Editing after residual | Changing factors on a `residual_calculated` assessment moves it back to `controls_in_progress` (or `scored`), so the residual must be confirmed again before submission. | Prevents submitting a stale residual. |
| D-32 | Dev identity | `DevAuthProvider` + `/dev/switch-user` let a developer pick a seeded user. No passwords. It refuses to run unless `APP_ENV=dev`. `PortalSessionAuthProvider` is the starting point for CU's real adapter. | PRD 2, 3. |
| D-33 | Risk Approver retired | At the client's request, the separate Risk Approver role is removed and its powers move to the **Privacy Team / DPO**: approving or rejecting Medium **and High** residual risks, and **accepting a risk for a limited time**. The DPO can also confirm Very Low (with the Reviewer). The Reviewer stays: it verifies evidence and approves Low / Very Low. Default routing is now High → DPO, Medium → DPO, Low / Very Low → Reviewer. Migration `0003` removes `risk_approver` role assignments and, if the active config still routes to it, saves the corrected routing as a **new** config version. This supersedes the Risk Approver parts of D-13 and D-16. Trade-off: High risks now need one sign-off instead of two; CU can restore two-person sign-off by routing High to `privacy_dpo, reviewer` in Admin → Scoring configuration. | Client decision (October 2026). |
